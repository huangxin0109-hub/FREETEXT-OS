# AI选书官 DeepSeek 接入技术方案 v0.1

> 所属产品：FREETEXT Bookstore OS  
> 所属模块：AI选书官  
> 当前阶段：真实 AI 判断 MVP 技术方案，不直接开发功能  
> 核心原则：AI做苦活，人做判断  
> 模型选择：产品内 AI 工作优先接入 DeepSeek API

## 1. 当前静态原型状态

当前静态原型已通过 GitHub Pages 上线：

- 在线地址：https://huangxin0109-hub.github.io/FREETEXT-OS/
- 已跑通 5 步路径：**首页 → 候选生成 → AI初筛 → 人工复核 → 最终清单**。
- 当前使用本地 mock 图书数据和预先写好的 AI 判断结果。
- 当前未接入真实 AI、库存、采购、登录或数据库。
- 两轮人工选书验证已经证明：现有 A/B/C/D 判断逻辑和 FREETEXT 选书规则具备进入真实 AI MVP 的基础。

当前原型已经验证了“怎么使用”，下一阶段需要验证“DeepSeek 能否稳定执行 FREETEXT 选书规则”。

## 2. 下一阶段目标

下一阶段只完成一个最小闭环：

1. 用户输入或选择一批候选书。
2. 前端将候选书信息发送到安全的最小后端接口。
3. 后端注入 FREETEXT 选书规则，并调用 DeepSeek API。
4. DeepSeek 返回每本书的 A/B/C/D 等级、推荐理由、风险提醒和人工复核问题。
5. 前端展示真实 AI 初筛结果。
6. 人逐本复核，决定是否进入最终候选清单。

本阶段不追求全自动，不优化 UI 细节。成功标准是：**把当前 mock AI初筛升级为真实 DeepSeek 初筛，同时保留人工最终判断。**

## 3. 核心资产与模型边界

FREETEXT OS 的核心资产不是 DeepSeek，也不是任何单一大模型。

真正需要长期沉淀的资产是：

- FREETEXT 选书规则。
- 自由文本书店气质的正面与反面案例。
- 候选书输入字段标准。
- A/B/C/D 输出标准。
- 人工复核结果与分歧原因。
- 持续更新的 KnowledgeBase。

DeepSeek 只是当前优先使用的**模型执行层**：负责读取规则、完成初筛、解释理由和整理结果。未来如果成本、质量、稳定性或业务需求发生变化，可以替换为其他模型，而不需要推翻 FREETEXT 选书规则和产品流程。

因此，代码中应把“选书规则”和“DeepSeek 调用”分开管理，避免把产品判断能力写死在某个模型中。

## 4. DeepSeek API 接入架构

推荐采用最小三层结构：

```text
GitHub Pages 前端
  ↓ 只提交候选书信息
安全的 Serverless 接口 /api/screen-books
  ↓ 注入 FREETEXT 规则并读取服务器环境变量
DeepSeek API
  ↓ 返回结构化初筛结果
Serverless 校验和整理结果
  ↓
前端 AI初筛页
  ↓
人工复核页 → 最终候选清单
```

### 4.1 前端层

继续保留当前 GitHub Pages 和 5 步页面路径。前端负责：

- 收集候选书信息。
- 调用 `/api/screen-books`。
- 显示“正在初筛、初筛成功、初筛失败”等简单状态。
- 展示 DeepSeek 返回的 A/B/C/D 结果。
- 保留人工复核和最终清单逻辑。

前端不保存 DeepSeek API Key，也不直接调用 DeepSeek API。

### 4.2 Serverless 接口层

新增一个最小 Serverless 接口：

```text
POST /api/screen-books
```

它只负责：

1. 接收候选书数组。
2. 检查字段是否完整、书目数量是否超限。
3. 从服务器环境变量读取 DeepSeek API Key。
4. 读取并注入 FREETEXT 选书规则。
5. 调用 DeepSeek API。
6. 要求 DeepSeek 返回结构化 JSON。
7. 校验返回字段和 A/B/C/D 等级是否合法。
8. 将安全、稳定的结果返回前端。

第一版可以选用支持环境变量和 Serverless Function 的简单部署平台。具体平台待代码阶段根据操作难度、费用和访问稳定性确定，优先选择非程序员容易维护的方案。

### 4.3 DeepSeek 模型层

DeepSeek 负责执行规则，不拥有最终决定权。

模型名称、API 地址和超时时间都应通过后端配置管理，不应散落在前端或业务逻辑中。第一版使用 DeepSeek 当前可用的通用对话模型，并保留以后替换模型的能力。

DeepSeek 官方 API 文档：

- API 文档：https://api-docs.deepseek.com/
- JSON Output：https://api-docs.deepseek.com/guides/json_mode
- 错误码：https://api-docs.deepseek.com/quick_start/error_codes

## 5. 为什么不能把 DeepSeek API Key 写进前端 app.js

绝对不能把 DeepSeek API Key 写入 `app.js`，原因很直接：

- GitHub Pages 的前端文件对所有访问者公开。
- 浏览器会下载 `app.js`，任何人都可以查看其中内容。
- 即使对代码进行压缩或隐藏，API Key 仍然可以被找到。
- 他人拿到 Key 后可以盗用额度、产生费用或恶意调用。
- Key 泄露后只能立即撤销并重新生成，且可能已经造成损失。
- 前端直连 DeepSeek 也无法可靠限制请求数量、输入大小和异常调用。

正确方式是：

- API Key 只保存在 Serverless 平台的服务器环境变量中，例如 `DEEPSEEK_API_KEY`。
- 前端只调用自己的 `/api/screen-books` 接口。
- Serverless 接口在服务器内部调用 DeepSeek，永远不把 Key 返回浏览器。

## 6. 前端需要改什么

第一版只修改与真实 AI 初筛有关的部分，不优化 UI 细节。

### 候选生成页

- 允许用户使用现有 mock 数据测试，或填写/粘贴候选书信息。
- 点击“开始 AI 初筛”后，将候选书发送到 Serverless 接口。
- 第一版建议每次最多提交 20 本，避免请求过大和等待过久。

### AI初筛页

- 将预先写死的 mock 判断替换为接口返回结果。
- 显示调用状态：等待、处理中、成功、失败。
- 展示 A/B/C/D、推荐理由、风险提醒、适合书架和人工复核问题。
- 接口失败时保留候选书输入，不让用户重新填写。

### 人工复核页与最终清单页

- 保持现有路径和判断权不变。
- 人仍然逐本选择“同意 / 修改 / 不接受”。
- 最终清单只能由人工复核结果生成，不能由 DeepSeek 自动决定。

## 7. 后端 / Serverless 需要做什么

第一版只需要一个接口和少量配置，不建设复杂后端系统。

### 最小职责

- 安全保存 `DEEPSEEK_API_KEY`。
- 接收并校验候选书数据。
- 限制单次书目数量和文本长度。
- 组合 FREETEXT 规则、任务说明和候选书数据。
- 请求 DeepSeek 返回 JSON。
- 校验和清洗 DeepSeek 返回结果。
- 返回统一的成功或错误格式。
- 不记录不必要的敏感信息。

### 最小安全措施

- 只允许预期的请求方法。
- 设置单次最多候选书数量，例如 20 本。
- 设置请求超时，例如 30 至 60 秒。
- 设置简单调用频率限制，避免 API 被公开滥用。
- 只允许已配置的前端站点来源调用；但必须认识到来源限制不能代替真正的访问控制。
- 不在错误信息中返回 API Key、完整系统提示词或服务器内部信息。
- 记录最少的错误类型和耗时，方便排查，不记录 API Key。

由于第一版不做登录，公开网页存在被他人调用接口的风险。因此 MVP 应设置严格的调用额度与频率限制，并在小范围测试。若准备开放给大量客户使用，再单独设计访问控制。

## 8. DeepSeek 输入字段

### 8.1 每本候选书字段

第一版优先发送以下字段：

| 字段 | 是否必需 | 说明 |
| --- | --- | --- |
| id | 是 | 前端生成的书目编号，用于匹配结果 |
| title | 是 | 书名 |
| author | 否 | 作者，缺失时必须标记信息不足 |
| publisher | 否 | 出版社 |
| publish_date | 否 | 出版时间 |
| category | 否 | 类别 |
| description | 是 | 内容简介，是判断的重要依据 |
| price | 否 | 定价 |
| is_recent | 否 | 是否近 3 个月新书 |
| inventory_duplicate | 否 | 由人填写的已知重复状态；第一版不接库存 |
| translator | 否 | 译者信息 |
| series | 否 | 所属系列 |
| source | 否 | 信息来源 |

### 8.2 本轮任务字段

- 本轮候选书数量。
- 希望最终保留的大致数量。
- 本月重点类别或主题。
- 本月需要排除的情况。
- 当前规则版本。

输入字段缺失时，DeepSeek 必须明确标记“信息不足，需要人工复核”，不能自行编造事实。

## 9. DeepSeek 输出字段

每本书必须返回：

| 字段 | 说明 |
| --- | --- |
| id | 与输入书目编号一致 |
| rating | 只允许 A / B / C / D |
| candidate_decision | 建议进入 / 观察 / 不建议进入 |
| reason | 2 至 3 句可理解的推荐或不推荐理由 |
| risks | 风险提醒数组 |
| shelf_theme | 适合书架或主题，无法判断时写待确认 |
| needs_human_review | 必须为 true；所有书最终都由人复核 |
| human_review_questions | 需要人确认的问题数组 |
| missing_information | 缺失但会影响判断的信息数组 |

每批结果还应返回：

- A/B/C/D 各等级数量。
- 建议优先复核的书目编号。
- 本批常见风险。
- 本轮需要人工补充的规则或信息。

## 10. A/B/C/D 结构化输出格式

建议 Serverless 要求 DeepSeek 返回类似以下 JSON 结构。此结构是接口约定，不是前端展示样式。

```json
{
  "rule_version": "v0.1",
  "results": [
    {
      "id": "book-001",
      "rating": "A",
      "candidate_decision": "建议进入",
      "reason": "该书主题与内容深度符合 FREETEXT 的文史哲方向，可作为本月重点候选。",
      "risks": ["出版时间需要人工确认"],
      "shelf_theme": "思想史",
      "needs_human_review": true,
      "human_review_questions": ["门店是否已有同类书过多？"],
      "missing_information": ["库存重复状态"]
    }
  ],
  "summary": {
    "total": 1,
    "rating_counts": { "A": 1, "B": 0, "C": 0, "D": 0 },
    "common_risks": ["库存信息缺失"],
    "rules_to_review": []
  }
}
```

Serverless 必须检查：

- 是否为合法 JSON。
- `results` 数量是否与输入一致。
- 每个 `id` 是否能匹配输入。
- `rating` 是否只包含 A/B/C/D。
- 是否错误地将 `needs_human_review` 设置为 false。
- 必需字段是否完整。

如果校验失败，应尝试一次修复或重新请求；仍失败则返回明确错误，不向前端展示不完整结论。

## 11. 提示词如何注入 FREETEXT 选书规则

提示词建议拆成四部分，避免把所有内容混在一起：

### 第一部分：固定角色与边界

明确告诉 DeepSeek：

- 你是 FREETEXT Bookstore OS 的 AI选书初筛助手。
- 你负责整理、初筛、解释和提醒风险。
- 你不能自动决定采购或上架。
- 所有结果必须经过人工复核。
- 信息不足时必须标记，不得编造。

### 第二部分：FREETEXT 选书规则

从经过人工确认的规则文件中读取，例如：

- 文史哲优先，社科次之。
- 艺术、设计、文学作为气质补充。
- 近 3 个月新书优先。
- 大众畅销但不符合 FREETEXT 气质的书慎选。
- 低质量拼凑书慎选。
- 数量保持克制。
- 库存、供货、译者质量等无法确定的信息必须交给人确认。

规则应有版本号，例如 `selection_rules_v0.1`。规则更新必须来自人工复核后的批准，不允许 DeepSeek 自己修改正式规则。

### 第三部分：结构化输出要求

明确要求只输出约定 JSON，说明所有字段、A/B/C/D 定义和禁止事项。使用 DeepSeek 支持的 JSON Output 能力，并在后端继续做格式校验。

### 第四部分：本轮候选书与任务信息

传入本轮候选书、本月重点、目标数量和排除条件。

长期方案中，规则与案例应独立于模型调用代码保存。这样更换模型时，只需替换模型适配层，不需要重写 FREETEXT 选书知识。

## 12. 错误处理方式

错误处理必须简单、明确，并保护用户已填写的内容。

| 情况 | 前端提示 | 系统处理 |
| --- | --- | --- |
| 候选书缺少书名或简介 | 请补充关键信息 | 不调用 DeepSeek |
| 请求超时 | AI 初筛暂时超时，请重试 | 保留当前候选书，可重新提交 |
| DeepSeek API 暂时不可用 | AI 服务暂时不可用 | 不生成假结果，不影响人工继续处理 |
| API Key 无效或额度不足 | AI 服务配置需要检查 | 后端记录错误，前端不显示内部细节 |
| 返回内容不是合法 JSON | AI 返回格式异常 | 后端尝试修复一次，失败则提示重试 |
| 部分书目结果缺失 | 本批结果不完整 | 不把缺失结果当成已判断，标记人工复核 |
| 触发频率限制 | 请求过于频繁，请稍后重试 | 拒绝额外调用，保护 API 额度 |

禁止行为：

- API 失败时继续展示旧 mock 结果，却让用户误以为是真实结果。
- DeepSeek 信息不足时自行编造作者、出版社、库存或供货情况。
- 因为模型表达流畅就跳过人工复核。

## 13. 不做什么

真实 AI 判断 MVP 坚决不做：

- 不优化 UI 细节。
- 不改变当前 5 步页面路径。
- 不接库存系统。
- 不接采购或自动下单。
- 不做登录、会员或多人协作。
- 不做复杂数据库。
- 不做复杂后台管理。
- 不做自动图书搜索和复杂爬虫。
- 不做销售预测。
- 不做多 Agent 系统。
- 不让 DeepSeek 自动决定最终候选清单或采购结果。
- 不把 DeepSeek API Key、完整系统提示词或敏感配置写入前端。
- 不把 FREETEXT 的核心能力绑定死在 DeepSeek 上。

## 14. 最小验收标准

真实 AI 判断 MVP 完成后，只检查以下事项：

1. 当前 5 步路径仍然可以正常使用。
2. AI初筛结果来自 DeepSeek，而不是预先写死的 mock 判断。
3. API Key 未出现在前端文件、浏览器请求内容或公开仓库中。
4. 每本书稳定返回 A/B/C/D、理由、风险和人工复核问题。
5. 信息不足时明确标记，不编造事实。
6. DeepSeek 调用失败时，用户输入不会丢失。
7. 人工复核仍然是进入最终清单的必要步骤。
8. 更换模型时，FREETEXT 规则和前端 5 步路径不需要重写。

## 15. Codex 下一步代码任务建议

完成本方案确认后，建议将代码任务拆成三个小步骤，不一次开发复杂系统。

### 任务 1：建立最小 Serverless 接口骨架

- 只新增 `/api/screen-books`。
- 从服务器环境变量读取 `DEEPSEEK_API_KEY`。
- 先使用固定测试输入调用 DeepSeek。
- 返回经过校验的结构化 JSON。
- 不修改人工复核和最终清单逻辑。

### 任务 2：将 AI初筛页接到真实接口

- 保留当前 5 步页面和 UI。
- 将 mock 初筛结果替换为 `/api/screen-books` 返回结果。
- 增加处理中、失败、重试状态。
- 确保失败时保留候选书输入。

### 任务 3：验证真实 20 本候选书

- 使用一轮真实候选书调用 DeepSeek。
- 人工逐本复核 A/B/C/D、理由和风险提醒。
- 记录与人工判断的差异。
- 判断是否达到继续推进标准，再决定是否增加规则版本管理或简单结果保存。

建议给 Codex 的下一条任务应先要求它读取本文件，然后只完成“任务 1”的技术实施方案与文件变更清单；确认后再写代码。

## 16. 当前最重要结论

AI选书官下一阶段不是开发一个复杂 AI 系统，而是完成一次最小、真实、安全的能力升级：

```text
当前静态 5 步原型
↓
安全 Serverless 接口
↓
DeepSeek 执行 FREETEXT 选书规则
↓
输出真实 A/B/C/D 初筛结果
↓
人完成复核和最终判断
```

必须始终坚持：

> FREETEXT 选书规则和知识库是核心资产，DeepSeek 是当前优先使用、未来可以替换的模型执行层。AI做苦活，人做判断。
